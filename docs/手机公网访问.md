# 手机公网访问

让顾客通过 HTTPS 链接直接在手机浏览器打开交互界面，不需要安装 App、连接同一 Wi-Fi，或保持店家电脑开机。

## GitHub Pages 静态演示（默认在线链接）

- 在线地址：https://tyza66.github.io/sunny-tea-house/
- 构建产物用相对路径发布；页面没有 `/api` 时自动使用本地示例文案，交互闭环完整可用。
- 后续修改源码推到 `main` 后，由 `.github/workflows/pages.yml` 自动构建并发布，无需额外命令。

## 为什么 GitHub Pages 上不用真实 AI，也不接免密钥公共接口

GitHub Actions 只在代码推送时执行构建。把 `AI_API_KEY`（旧名 `DEEPSEEK_API_KEY`）注入构建，密钥会随公开仓库的前端产物一起发布出去；网页本身也无法同步等待一个 workflow 跑完再返回评价。所以 Pages 只能承载静态前端，服务端逻辑（密钥、限流、长度修正、企业微信通知）必须放在 Netlify Functions 或自有服务器上。真实 AI 生成请按 `AI服务商接入.md` 配置。

考虑过直接用免密钥的公共文本接口（实测 `text.pollinations.ai`，2026-09-24）：

- 简单中文请求约 10 秒返回，内容却是与本店无关的餐馆段子。
- 带店名和“不得编造经历”约束的英文请求约 12 秒返回。
- 加拿大法语请求 30 秒无响应、零字节，直接超时。

这类接口没有可用性承诺，耗时随负载大幅波动，也没有调用方限流保护，更不接受“小红书不超过 150 字符”“不得捏造饮品、价格、购买次数”这两条硬约束。接进来只会把不可控的等待和编造内容转嫁给顾客，最终仍要人工返工，与项目目标冲突，因此不接入。静态演示继续使用本地模板文案，界面也明确标注“不会调用 AI 服务”。
## 部署到 Netlify 后

- 已部署到 Netlify：前端静态资源 + `netlify/functions` 提供 `/api/config`、`/api/reviews`。
- Netlify 端固定为真实模式（演示开关已在该路径关闭），因此**必须配置 `AI_API_KEY`**；未配置会报错而非演示。
- 页面右上角为“AI 评价助手”，生成走 `AI_BASE_URL` 指定的服务商真实接口（默认 DeepSeek）。

## 手机使用

1. 在手机浏览器打开发布后的 HTTPS 链接。
2. 选择界面语言、评价语言、感受标签和平台，点击生成。
3. 修改文案，核对后勾选确认，再复制。
4. 若手机浏览器限制自动复制或弹窗，用文本框长按复制，并使用页面的手动平台链接。

页面采用标准网页技术，面向 iOS Safari、Android Chrome、鸿蒙等现代浏览器。不能保证已停止维护的旧浏览器或所有第三方内置浏览器行为一致；不同地区网络也可能影响访问，最终以真实手机与网络打开链接确认。

## 构建与部署

- 本地运行：`npm.cmd run build`，然后 `npm.cmd start`（后端 + 前端）。
- 部署 Netlify：见 `AI服务商接入.md`。用 `部署到Netlify.cmd` 或仓库连接，**不要拖拽整个文件夹**（会带大量无关文件且函数部署不正确）。
- 后续修改源码后，用同一个网站地址重新发布。

## 密钥与安全

- AI Key 只放在服务端/Netlify 环境变量，**不要填进网页或提交到版本库**（`.env` 已 gitignore）。
- 真实生成会消耗所配置服务商账户的余额，也受 Netlify 当前免费套餐额度约束。
